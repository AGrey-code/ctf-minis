Patient Zero

Forensics mini-challenge · beginner · about 5 minutes

Your mission

A workstation was compromised. Security software captured a 204-line log of process activity around the time of the incident. Somewhere in it, one process ran a malicious executable. Find the PID (process ID) responsible.

Most processes in a log like this run once and disappear. The process you're after was busy: it shows up on far more lines than an ordinary one-off process. Figure out how to count that, narrow down the top candidates, then look closely at what each one actually did.

The flag is CTF{PID}, where PID is that process's ID number. For example, if the PID were 1234, the flag would be CTF{1234}.

Terminal

Type help to see available commands, including pipes with |, just like a real shell. Start with ls.

investigator@forensics:~$

Check your flag

Stuck?

Hint 1. Run ls, then cat system.log to see the format. Each line has a PID, a parent PID (PPID), a user, a full program path, and a status. 204 lines is too many to read one by one. You need to count how often each PID appears, and find the one that stands out.
Hint 2. This terminal supports piping with |, just like a real shell. There's also a helper command, pids, that turns each log line into just its PID. Try: cat system.log | pids | sort | uniq -c. Notice that uniq -c only counts matches that are next to each other, which is why you sort first.
Hint 3. That gives you a count for every PID, but it's still a long list. Sort it again, this time by the count itself, and keep only the top few: cat system.log | pids | sort | uniq -c | sort -nr | head. Then inspect each of the top PIDs one at a time with grep <PID> system.log. Most will turn out to be ordinary repeated background activity.
Last hint: the answer. Only open this if you have tried the earlier hints.

Count and rank PIDs by frequency:

cat system.log | pids | sort | uniq -c | sort -nr | head

PID 6650 comes out on top, appearing 6 times, well above the next busiest PIDs (4 times). Inspect its full history:

grep 6650 system.log

The first five lines look like ordinary svchost.exe activity. The sixth does not:

[2024-03-15 14:17:30] PID=6650 PPID=8359 USER=agupta     PROC=C:\Users\agupta\AppData\Local\Temp\suspicious_evil_virus.exe STATUS=BLOCKED

The flag is CTF{6650}.

Why this worked

This is log analysis, one of the most common forensics tasks. In a real log, an attacker's process is often doing more than a normal one, probing, downloading, waiting, trying again, so it leaves more traces. Counting how often each identifier shows up, and looking closely at the busiest ones, is a real triage technique investigators use on logs far too long to read line by line.

Notice the log also shows PPID=8359, the parent process that launched the malicious executable. In a real investigation, that's the next thread to pull: what process is 8359, and how did it get onto this machine?
